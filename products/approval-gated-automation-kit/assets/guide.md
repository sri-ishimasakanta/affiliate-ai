# 5つの自動化の段階で作業を分ける手引き

AIを使った自動化は、「全部を任せる」か「全部を手でやる」かの二択ではありません。作業ごとに、
どこまでを自動にし、どこで人が止めるかを先に決めておくと、任せる範囲を安全に広げられます。
この手引きは、実際に記事・投稿・運用の自動化を組む中で使ってきた分け方を、特定のサービスに
依存しない形にまとめたものです。

## 5つの段階

| 段階 | 意味 | 例 |
|---|---|---|
| A 読むだけ | 人がいなくても動く。手元の分析や記録だけを書く | 数字の集計・点検・候補の洗い出し |
| B 上限の中で自動 | 人が決めた上限の中だけで、自分で動く | 承認済みの投稿を、決めた間隔と 1 日の上限で出す |
| C 1 件ずつ承認 | 人が 1 件ずつ承認し、その内容だけを既存の仕組みが実行する | 記事の書き換え・新しい投稿の案 |
| D 初回は人が有効にする | 仕組みは作ってあるが、最初の 1 回を人が確かめるまで無効 | 新しい種類の書き込み・初めての自動メール |
| E 自動にしない | 仕組みでは行わないと決める | トラッキングの変更・すべて承認・他人への自動返信 |

## 進め方

1. 書き込み先を一覧にし、上の表のどれかに置きます。迷ったら 1 つ下 (より人が関わる側) に
   置きます。後から上げるのは簡単ですが、事故の後に下げるのは大変です。
2. C の作業は、承認を内容の hash に結びつけます。承認の後に内容が変わったら、承認は効かなく
   なります。これで「承認した後に誰か (または AI) が書き換えた」ことを防げます。
3. D の作業は、設定の既定を「無効」にしておきます。最初の 1 回を人が見届け、問題が無ければ
   有効にします。この判断は記録に残します。
4. 「提案の承認」と「書き込みの承認」を分けます。分析が「この記事を直すとよい」と提案し、
   それを認めても、記事の書き換えはまだ起きません。書き換えは、書き換えの内容そのものを別に
   承認したときだけ行います。

## ファイルと生成物の承認を固定する

文章だけでなく、画像・添付ファイル・生成した成果物も承認の対象になります。ここで気をつけたいのは、
**ファイル名やパスでは、承認した物を固定できない** ことです。承認の後に、同じパスへ別の中身が
上書きされることがあります (作り直した画像を同じ名前で保存した、など)。人が承認したのは
「その時点の中身」であって、「そのパスにあるもの」ではありません。

そこで、次の流れにします。

1. **提出**: 承認してほしい中身を出します。この時点で中身の hash を計算します。
2. **承認**: 人は中身を見て承認します。記録には、承認した人・時刻と、中身の hash を残します。
   元のファイルが後で変わりうるなら、承認した中身の写しを、上書きも削除もしない場所に
   中身の hash の名前で置きます。承認の後は、この写しが正本です。元のファイルは
   「どこから来たか」の記録として残すだけにします。
3. **使う前の照合**: 実行・公開の直前に、承認した hash と実際に使う中身を照らし合わせます。
   写しがあれば写しを使い、写しが無い・中身が違う、なら止めます。
4. **変わったら**: 中身を変えたいときは、古い承認を流用しません。承認を取り消し、変えた中身を
   出し直し、もう一度承認します。同じ中身なら同じ hash になるので、前の写しをそのまま使えます。
5. **履歴**: 効かなくなった承認も消さず、取り消した理由と時刻をつけて残します。過去の承認が
   どの中身に対するものだったかを、後からたどれるようにします。
6. **事後の承認**: 公開の後にしか確かめられなかった場合は、「公開の後に承認した」ことを記録に
   書きます。公開の前に承認したかのように、時刻や順番を書き換えません。

## よくある落とし穴

- **取り戻し**: 止まっていた間の分をまとめて出すと、上限や間隔の意味が無くなります。止まって
  いた分は捨てるか、次の枠に 1 つずつ回します。
- **結果の分からない書き込み**: 通信が途中で切れたとき、成功したと決めつけないでください。
  次に読み戻して確かめるまで「分からない」として記録します。
- **通知の出しすぎ**: 正常の通知や同じ問題の繰り返しは、本当に必要な通知を埋もれさせます。
  行動が要るときだけ知らせ、同じ問題は 1 つにまとめます。
- **同じパスの上書き**: 承認の後に、同じ名前のファイルを作り直して保存すると、承認していない
  中身が承認済みのように扱われかねません。承認は中身の hash に結びつけ、使う前に照らし合わせます。
- **古い承認の使い回し**: 中身を少し直しただけでも、前の承認は別の中身に対するものです。
  「小さな直しだから」と承認を引き継がず、承認し直します。

## この手引きで言えないこと

この分け方で事故がなくなる、あるいは収益が上がる、とは言えません。確かめられるのは、誤った
書き込みを止める場所がはっきりすること、承認した物を中身で固定しやすくなること、中身が
変わったときに古い承認を流用しない運用にできること、までです。自分の仕組みに当てはめ、記録を見ながら
段階を調整してください。
