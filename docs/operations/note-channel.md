# note チャネル (N0: 土台)

N0 は note チャネルの **ローカルの土台** である: 位置づけ・段階の境界・下書きの形・材料の
出どころ・重複 / 秘密 / 事実の規則・候補の発見と採点・人の確認の約束。**note への公開・
下書きの保存・ログイン・アカウントの作成はしない。**

N0 の定義について: リポジトリには N0 の中身の定義が無かった (roadmap の `declared_only`・
T7C の決定の「次のフェーズは N0」だけ)。この文書の定義は、N0 を始めるときに人が示した目的
(note を「作りながら記録する」開発日誌のチャネルにする) にもとづく。

```bash
uv run python scripts/propose_note_content.py              # 候補を表示するだけ (何も書かない)
uv run python scripts/propose_note_content.py --write      # reports/note/candidates_latest.json
uv run python scripts/propose_note_content.py --draft top  # 一番の候補のローカルの下書き
```

コード: `app/social/note/` (Threads と同じ `app/social/` の下のチャネル)。出力は
`reports/note/` (git 管理外) だけ。ネットワークも LLM も使わない。

## 位置づけ

| チャネル | 役割 |
| --- | --- |
| WordPress | 検索の意図に答える、磨いた SEO / アフィリエイトの記事。根拠と収益化 |
| Threads | 見つけてもらう入口。短く単体で役立つ投稿。人の承認 + 自動公開の安全の型 |
| note | 開発日誌 (作りながら記録する)。決めたこと・試行錯誤・変えたこと・結果・学び |

作業上の見出し (公開のプロフィールに使うとは限らない):
「AIで収益メディアをどこまで自動化できるか。実際に作りながら記録する。」

note の記事は初心者が読める文章にする。WordPress の記事の写しでも、エンジニアの作業ログの
転記でもない。更新の目安は週 2 本程度だが **目安であって不変条件ではない**。

## 段階 (N0 / N1 / N2 / N3)

| 段階 | すること | 公開 |
| --- | --- | --- |
| **N0** (この段階) | 土台・約束・材料の選び方・安全の検査・ローカルの候補と下書き | **しない** |
| N1 | 最初の 1 本: 候補から人が 1 つ選び、下書きを人と整え、人が最終の題名と本文を承認する。公開は人が note の画面で行う (初めての公開の確認点) | 人の手で 1 本だけ |
| N2 | 繰り返せる制作と確認の流れ (候補 → 下書き → 確認 → 公開の記録)。公開の証拠 (URL) を記録に戻す | 人の手で |
| N3 | 運用の成熟: 計測 (読まれ方)・更新の目安の見直し・自動化の一部 (人の承認は残す) の検討 | 人の判断で |

N1・N2・N3 は宣言だけで、まだリポジトリに作業は無い。N0 は外部への公開の前で止まる。

2026-09-30 に N 系の順番を C10 → N1 → … → N8 → C11 とし、N4〜N8 (知識の商品化・デジタル商品の自動化・システムの製品化・SaaS の検証・SaaS / サービス。人が 2026-09-30 に正式に定義) を加えた。note と WordPress・Threads のつなぎと有料 note の記録は N1〜N4 に置いた。各段階の定義 (目的・入る条件・範囲・今作れるもの・本物のサービスやデータが要るもの・人の確認点・完了の定義) と依存の図は [n-track-plan.md](n-track-plan.md)。

## 下書きの形 (`app/social/note/models.py`)

- `NoteCandidate`: id・型・仮の題名・前提・出来事の ID (source event)・フェーズ・根拠
  (`EvidenceRef`)・根拠のそろい具合・役立つ理由・重複の危険・採点の内訳・警告。
- `NoteDraft`: id・候補の id・型・仮の題名・前提・読者・要約・節 (本文)・主張 (`Claim`)・
  フェーズ・出来事の ID・WordPress / Threads の参照・作成時刻・状態・`content_hash`・
  `generator_version` (`note-foundation/1`)・警告・誤り・`human_review_required` (常に true)・
  承認の記録・公開の記録。
- `Claim`: 文と種類 (`observed_fact` / `decision` / `hypothesis` / `interpretation` /
  `planned`) と根拠。観測した事実と決定は根拠が無いと誤り (`review_ready` にできない)。

状態は小さく: `draft` → `review_ready` → `approved` → `published` / `rejected`。

- `approved` は人の承認の記録 (`approved_by`・`approved_at`・承認した `content_hash`) が要る。
  本文が変われば hash が変わり、承認は効かない。
- `published` は公開の証拠 (`url`・`observed_at`) が要る。証拠の無い「公開済み」は作れない。
- N0 の下書きはすべて `draft`。

## 材料の出どころ (`app/social/note/sources.py`)

強い順 (T7 の出どころの強さ `precedence` の名前を使う):

1. プロジェクトの状態の報告 (`reports/project_state_latest.json`。本番を読んだ事実)
2. `docs/project-roadmap.json` (完了したフェーズと commit)
3. 決定の記録 (`docs/decision-log/*.md`)
4. 運用のドキュメント (決まった言い回しが今もあることだけを確かめる)
5. (任意、重複の検査だけ) アプリの DB の記事本文と Threads の公開文 (SQLite は `mode=ro`)

使わないもの: 生のログ (worker のログなど)・秘密を含みうるファイル・推測・作業のセッションの
記録。各主張は根拠を持ち、下書きの Markdown の「根拠」の節 (公開の前に消す) に並ぶ。

## 型 (v1、`app/social/note/catalog.py`)

| 型 | 目的 | 最低限の根拠 | 書いてはいけないこと |
| --- | --- | --- | --- |
| `build_log` | 何を作ったか・なぜ | 完了したフェーズ + その決定の記録 | 観測していない効果 (収益が増えた、など) |
| `decision_note` | 意味のある決定と理由 | 決定の記録 (理由と結果つき) | 比べていない選択肢への断定 |
| `experiment_result` | 試したこと・起きたこと・変えたこと | 試した記録と結果の記録 | 少ないサンプルからの因果・一般化 |
| `milestone_recap` | 節目のまとめ | 完了したフェーズ 2 つ以上 + 報告の事実 | 手数料の記録が 0 件のあいだの収益の成果 |

話題はコミットごとに作らない。まとまった出来事 (完了したフェーズ・長く効く決定・運用の
学び) だけを `TOPICS` に置き、発見のときに根拠が今もあるかを確かめる。

## 重複を避ける (変換の型)

出来事 → 前提 (何のための話か) → 決めたこと / 試したこと → 観測した結果 → 学び → まだ
分からないこと。本文はリポジトリを見たことのない読者が単体で読めること。

- 本文に内部の言葉を出さない: フェーズの記号 (W1・T7・N0 など)・記事の内部 ID・CLI の flag・
  内部の項目名を含む主張は本文から外し (警告)、根拠の一覧にだけ残す (`safety.reader_facing`)。
- 重複の検査 (`safety.duplication`): 本文の文字 3-gram のうち、WordPress の記事本文・Threads の
  公開文・内部のドキュメント (`docs/operations/*.md`・状態の報告の Markdown) にもある割合。
  0.5 以上は `duplicate` (誤り)、0.3 以上は `similar` (警告)。

## 秘密・内部の安全 (`app/social/note/safety.py`)

T7 の `redaction.redact_text` (token・Bearer / Basic・URL の認証情報・`/go/`) に加えて、
ローカルの絶対パス・メールアドレス・端末名・32 桁以上の digest・承認 / capability の URL・
ロックの token などの内部の値を伏せる。T7 の報告にあるからといって、運用のセキュリティに
関わる詳細を記事に出さない。

## 事実の安全

- 観測した事実・決定・仮説・解釈・予定を分ける (`Claim.kind`)。
- 収益の主張 (「収益が伸びた」など) は、手数料 (commission) の記録があるときだけ。記録が
  0 件なら誤りにする。0 件を成功として書かない (`milestone_recap` は 0 件であることを書く)。
- 因果の言い切り (「〜のおかげで」「効果があった」) は警告。少ないサンプルから結論を出さない。
- 煽りの言葉 (Threads と同じ禁止の言い回し) は警告。

## 候補の採点

優先度のためだけ (公開を決めない)。各 0〜3 の整数の和から重複の罰点を引く:
役立ち (型ごと)・新しさ (同じ出来事の承認済み / 公開済みの下書きが無いか)・根拠のそろい具合・
節目の大きさ (完了したフェーズの数)・初心者の読みやすさ (編集判断)・新しさ (最近の 3 つの
完了フェーズに触れるか)・重複の罰点 (low 0 / medium 1 / high 2)。同点は id 順。根拠が必要な
数の半分に満たない話題は候補にしない。

## 人の確認の約束

公開は当面すべて人の確認つき。人が承認するもの:

- 最終の題名
- 最終の本文 (承認は `content_hash` に結びつく)
- 外部へのリンク
- 画像・スクリーンショット
- 公開の操作そのもの

元の出来事 (フェーズの完了など) を承認したことは、note の記事を承認したことにはならない。
N0 は自動公開を作らない。

## 外部の公開 (調べただけ。有効にしていない)

- このリポジトリに note の連携 (API・資格情報・設定) は無い。
- 知る限り、note には一般に公開された投稿用の公式 API が無い。非公式の方法は保証が無く、
  規約の面でも使わない。公開は人がブラウザの note の編集画面で行う前提にする (N1 で最新の
  状況を確かめる)。
- 必要になるもの: 人の note アカウント (人が作る・人がログインする)。このリポジトリに
  資格情報は置かない。
- 人の確認点: 最初の公開 (N1)。公開の後、人が URL を記録に戻す (N2 で形を決める)。

## プロジェクトの状態との関係

`scripts/generate_project_state.py` の `project.note_channel` に、N0〜N3 の状態・候補の数・
下書きの状態・公開の数 (公開の証拠があるものだけ)・人の確認待ちを出す
(`app/project_state/note_state.py`。`reports/note/` を読むだけで、note には問い合わせない)。
警告にはしない。スケジュールされたタスクは作らない。

## 後の段階の計測の案 (N3)

読まれ方 (note の閲覧・スキ) は人が手で記録するか、公式の手段があれば使う。WordPress への
流入は GA4 の参照元で見る。note の数字からも、少ないサンプルで因果を言わない。
