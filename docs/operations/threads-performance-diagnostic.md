# Threads の成績の診断 (経過時間をそろえた比較、読むだけ)

「最近の投稿は views が落ちているか」を、**公開からの経過時間をそろえて** 答えるための
診断。何も変えない (生成・学習・並び順・公開の時刻や頻度には一切つながない)。

```bash
uv run python scripts/analyze_threads_performance.py
uv run python scripts/analyze_threads_performance.py --as-of 2026-09-25T21:00:00+09:00
uv run python scripts/analyze_threads_performance.py --output-dir D:/tmp/reports --json
```

出力: `reports/threads_performance_diagnostic_latest.json` と `.md`
(`reports/` は git の管理外。本番のデータを含む実行時の成果物)。

## なぜ生の views では比べられないか

views は Threads が返す **累積値** で、公開からの時間とともに増える。公開 40 時間の投稿の
146 views と、公開 1.5 時間の投稿の 41 views を並べても、後者が弱いとは言えない。
報告の §1 は生の値を「比べられない」と明記して載せ、§2 以降は同じ経過時間で比べる。

## 経過時間とチェックポイント

- 起点 (age 0) は **実際の公開時刻** (`ThreadsPublicationService.gap_basis`:
  Threads の `remote_timestamp` → 公開 API の成功 → 照合 → 記録の順)。保存済みの
  `age_hours` は手元の `published_at` から測っているので使わず、観測時刻から測り直す。
- チェックポイント: **1h / 3h / 6h / 12h / 24h / 72h**。診断のためだけの区切りで、T5 の
  成熟 (72h) の規則は変えない。

## 観測との対応と許容幅

- チェックポイントに **最も近い本物の観測** を 1 つ選ぶ。同じ距離なら早い方 (累積値が小さい
  = 控えめ)。**補間しない**。累積値は累積値のまま (区間の伸びは本物の 2 点の差だけ)。
- 公開前の観測・失敗した観測 (`failed` / `empty`)・views が欠けた観測は使わない。
- 許容幅 = `min(max(15 分, その経過時間での収集間隔), チェックポイントの 50%)`。収集間隔は
  `threads_operations_policy.json` の `insights_refresh.interval_minutes_by_maturity`
  (いまは 1–24h が 30 分、24–72h が 60 分、72h 以降が 6 時間) → 1h/3h/6h/12h は ±30 分、
  24h は ±60 分、72h は ±6 時間。外れたら「比較できない」とし、値は使わない (0 にしない)。
- 実際の収集は、worker の停止や読み取りの失敗で間が空くことがある (公開 #1 は 0.5h の次が
  16.7h)。その場合は該当のチェックポイントが「比較できない」になる。

## 判定 (スコアは無い)

チェックポイントごとに、比較できる投稿を公開順に並べて判定する。根拠の値は必ず添える。

| 状態 | 条件 |
| --- | --- |
| `insufficient_data` | 比較できる投稿が 3 本未満 (傾向を言わない) |
| `directional_decline_signal` | 直近 3 本が狭義に減少 **かつ** 最新が「それより前の中央値」の 70% 以下 |
| `no_clear_decline` | 最新が「それより前の中央値」の 90% 以上 |
| `mixed` | それ以外 (1 本だけ弱い、など) |

確度: 3 本は `very_low`、4–5 本は `low`、6 本以上で `moderate`。全体の状態は、3 本以上
そろったチェックポイントの判定がすべて同じならそれ、違えば `mixed`、そろったものが
無ければ `insufficient_data`。1 本だけ弱い投稿は「繰り返しの低下」とは区別する
(直近 3 本の減少を条件にしているため)。

## その他の内訳 (記述だけ)

- **初速**: 公開→1h、1h→3h、3h→6h の伸び (本物の累積値の差 / 実際の時間)。初めの配信が
  弱いのか、初めは伸びて止まったのかを区別するため。原因 (アルゴリズム) は推測しない。
- **次元**: 切り口・リンク・トピック・長さ (T4 の帯)・時間帯 (T5 と同じ測定ポリシーの
  `learning.dayparts`)。本数が少なければ `small_sample`。中央値を使う。
- **相互作用**: likes / replies / reposts / quotes / shares と合計の比。views が 30 未満
  (T4 の `minimum_views_for_ratio`) では比を出さず件数だけ。views (届いた量) と相互作用
  (反応の質) は別に読む。views が少なくても反応の率が高い投稿を「悪い」とは言わない。
- **似かより**: URL を除いた本文の文字 2-gram の Jaccard (連続する投稿どうし・最も似た組)、
  2 本以上に出る 10 文字の同じ言い回し、切り口の並び、同じトピックの連続。ブランドの
  共通表現は欠陥として扱わない。

## 手動・管理外の投稿

同じアカウントに人が手で投稿すると、間隔 (120 分) の解釈・成績の比較・学習のデータの
どれもが不完全になる。ただしこのリポジトリの Threads client には **アカウントの投稿一覧を
読む API が無い** ので、検出は `unavailable` と報告する (新しい API 呼び出しは足していない)。
手元の media id と一覧を突き合わせる純粋な関数 (`compare_media_ids`) は用意済みで、一覧を
読む読み取り専用の API を足せば使える。報告には、最後の観測が 404 (見つからない) だった
手元の公開も載せる。

## T5 / T5.5 との違い

| | この診断 | T5 / T5.5 |
| --- | --- | --- |
| 目的 | 同じ経過時間での記述 (落ちているか) | 成熟した投稿の比較と、生成への弱い参考 |
| 使う観測 | 1h〜72h のチェックポイント | 72–96h の窓の代表の観測 1 つ |
| 影響 | **なし** (報告だけ) | T5.5 は新しい提案の prompt にだけ効く |

この診断の結果を生成の重み・並び順・参考・公開の時刻に使わない。

## 読むだけの保証

- DB に書かない (`read_only_session` で flush を止める)。観測を取り直さない。保存済みの
  指標を書き換えない。
- Threads に問い合わせない (公開時刻の計算に渡す Threads の代役は、呼ばれたら例外にする)。
- 書くのは `reports/` の 2 ファイルだけ。
