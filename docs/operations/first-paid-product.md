## 無料と有料の境界 (最有力の候補で)

無料の記事を、有料に誘うために薄くはしない。境界は「考え方・理由・経緯」と「自分の環境で使う
道具」の違いで引く。

| 無料 (note の無料記事・続けて書く) | 有料 (この product) |
|---|---|
| なぜ承認と公開を分けたか、5 段階の考え方の概要 | 5 段階に作業を置く手順と迷ったときの決め方 (手引きの全文) |
| 実際に決めたこと・その理由 | 20 項目のチェックリスト (書き込み先ごとに確かめる形) |
| 失敗と学び (例: 承認の後に画像が上書きされた → 写しを正本に) | 既定がすべて安全側の設定例 (JSON)。そのまま写して直せる |
| 今の状態・まだ分からないこと | よくある落とし穴 (取り戻し・結果の分からない書き込み・通知の出しすぎ) の確認 |
| | 版と変更の記録 (更新したら同じ物で読める) |

## note の有料記事として出す場合の構成案 (まだ出さない)

- **題名の案**
  1. AI自動化に「人の承認の門」を組み込む：20項目のチェックリストと設定例
  2. 承認してから公開する。AI自動化を安全に広げるためのチェックリストと設定例
  3. 「全部任せる」と「全部手で」の間：作業を5段階に分ける承認の設計キット
- **想定読者**: AIで記事・投稿・運用の作業を自動化し始めた、個人や小さなチームの運営者。
- **解決する問題**: 任せる範囲が広がるほど、誤った書き込みや公開をどこで止めるかが曖昧になり、
  一度の承認が別の書き込みまで許してしまう。
- **無料の部分 (有料の区切りの前)**: 誰のための物か・扱う問題・同梱の一覧・**含まないこと**
  (`known_limitations` の 4 つ)・無料の記事 (controlled #1) へのリンク・版。
- **有料の部分**: 手引きの全文 → チェックリスト → 設定例 (コードの枠) → 使い方 → 注意事項 → 変更の記録。
- **同梱の資産**: 手引き・チェックリスト・設定例を本文に載せる (zip の配布は別の配布先が要るので、
  決めるのは人)。本文は H5 で承認した版の資産と同じにする。
- **使い方**: (1) 書き込み先を一覧にする → (2) 5 段階に置く (迷ったら人が関わる側) →
  (3) チェックリストで「はい」にできない項目を残す → (4) 設定例を写し、既定は無効のまま、
  最初の 1 回を人が確かめてから有効にする。
- **注意事項**: 事故がなくなる・収益が上がるとは言えない (観測した結果ではない)。設定例の数値は
  例で推奨値ではない。特定のサービスの手順・コードは含まない。秘密は設定に書かない。
- **主張と根拠**: 言うのは「誤った書き込みを止める場所がはっきりする」まで (手引きの「言えない
  こと」と同じ)。根拠の対応は review packet にあり、読者向けの本文には出さない。
  使わない言葉: 稼げる・売上が増える・必ず成功する・時間が何%減る・CV が上がる・自動化すれば
  利益が出る。
- **更新の方針**: semver。言い回し・誤りの修正は patch、項目の追加は minor (例: 承認した画像を
  中身の hash の写しで固定する項目を足すなら 0.2.0)。出どころが変われば `plan` が知らせる。
- **版の表記**: 本文の最後に「版 0.1.0」と変更の記録。手元では manifest の hash で版を固定する。
- **変更の記録**: 本文の最後の節。版ごとに 1〜3 行。過去の版の記録は消さない。
- **価格 (決めない。判断の材料だけ)**: 案 A 低め (最初の 1 本で買う側の不安を小さく)・
  案 B 中くらい (チェックリストと設定例をそのまま使える分を反映)・案 C 高め (更新を続ける約束と
  組み合わせる場合)。材料: 同梱の量 (約 7.4 KB の本文)・まだ買われた実績が無い・note の手数料と
  有料記事の条件 (人が最新の条件を確かめる)・更新の頻度をどこまで約束するか。

## 最初の有料記事を公開できる条件 (公開の門)

すべてを満たすまで有料で公開しない。

1. product の中身の人の確認 (H4 の `review --confirm-all`) と内容の承認 (`approve-content`)。
2. 主張の確認 (効果を言っていない・出どころと合う。`check` の 0 errors)。
3. 秘密・このサイトの値が無いこと (`check` と `validate` の redaction)。
4. build の検査 (`verify` で同じバイト・`validation_errors` 空)。
5. 版と変更の記録が決まっている (`CHANGELOG.md` に `## <版>`)。
6. 無料と有料の境界を人が確かめた (無料の記事を薄くしていない)。
7. 販売の価格を人が決めた。
8. 有料記事の本文を人が確かめた (note の承認の流れ。`access-mode paid` で承認し、本文の hash に
   結びつける。本文は H5 で承認した版の資産と同じ)。
9. release の承認 (H5 `approve-release --manifest-hash <hash>`)。
10. 公開の行為そのもの・販売の開始は人が note で行う。

- **N3 の 4 週間は条件ではない。** この product は実測の数を主張に使わない (効果を言わない)ので、
  N3 の完了を待たずに公開できる。
- **ただし**、販売のページや本文で N3 の数 (読まれた数など) を使うなら、N3 の完了 (3 本以上 ×
  4 週間以上) まで待ち、そのときも因果を言わない。
