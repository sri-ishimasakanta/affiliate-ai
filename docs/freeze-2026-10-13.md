## Resume procedure (do not enable tasks first)

1. The human explicitly approves resuming.
2. `git pull`; confirm branch `main`, HEAD, a clean tree.
3. Confirm the production DB opens, `integrity_check` ok; compare with the freeze backup.
4. Check credential validity (Threads token, WordPress application password, OpenAI, Google, SMTP)
   without printing them.
5. Review external API / provider changes since the freeze (Threads API, WordPress, ASPs).
6. Decide whether dependencies need updating (`uv sync`).
7. `uv run alembic current` / `heads`; must match.
8. Check `PENDING_PRODUCTION_MIGRATIONS` and any new migrations.
9. `uv run ruff check .`
10. Tests (`uv run pytest -q`; CLI tests read the default DB, so prefer an isolated copy).
11. `uv run python scripts/generate_project_state.py --strict` (while frozen it reports the disabled
    tasks; after resuming it must be ok).
12. Read-only external connectivity (`scripts/check_threads_connection.py`, WordPress read).
13. Threads: reconcile **#113** first (`scripts/publish_threads_post.py --reconcile`, read-only
    check of the post), then one read-only account-post discovery
    (`scripts/manage_threads_account_posts.py discover --execute`).
14. WordPress: confirm the 25 articles and the `/go/` redirects.
15. ASP: record any result that arrived (Krisp) with `scripts/affiliate_inventory.py verify`.
16. Review the publication queue (approved / awaiting proposals; reject stale ones by hand).
17. Compare each scheduled task's definition with the pre-freeze XML in the runtime snapshot.
18. Start the worker once under control (`Start-ScheduledTask` after enabling only the worker, or a
    one-off run), and watch the first cycle.
19. Health check: worker log, project-state, no errors.
20. Only then enable the other scheduled tasks.
